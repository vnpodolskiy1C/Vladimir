# План реализации HTTP-сервиса счетов магазина

> **Для исполнителя:** применять `subagent-driven-development`, поручать задачи
> субагентам последовательно; прогресс хранить в журнале плана. Независимое ревью — перед
> загрузкой и после завершения приёмки.

**Статус:** реализация и HTTP-приёмка завершены. Пользователь подтвердил счёт в Предприятии и принял результат.

**Цель:** магазин создаёт проверенный штатными средствами непроведённый счёт,
используя самоописание сервиса и поиск существующих ссылок.

**Архитектура:** HTTP-сервис в расширении делегирует обход метаданных и преобразование
значений серверным общим модулям. Схема — единый источник правил для приёма данных,
выдачи ссылок и чтения результата. Штатная проверка и запись выполняются в транзакции.

**Стек:** Hierarchical XML и BSL платформы проекта; Node.js со встроенными средствами
HTTP и тестирования; REST Client; CLI стенда для операций 1С.

**Спецификация:** [утверждённый контракт](../specs/2026-10-25-shop-invoices-design.md).
Публичные имена, пути, лимиты и статусы брать оттуда до появления реализации;
прикладные поля — из метаданных. Их ручной перечень в плане не нужен.

## Общие ограничения

- Правила проекта и изменяющих команд — [AGENTS.md](../../../AGENTS.md).
- Исходники расширения и тестов — в `src/`; основную конфигурацию не менять.
- Не расширять согласованные операции, не включать привилегированный режим.
- Не обходить штатную проверку, не рассчитывать суммы и не заполнять реквизиты за магазин.
- Создание контрольного документа входит в приёмку; остальные изменения данных
  и настроек требуют отдельного согласования.
- Каждый запуск загрузки — после отдельного согласования показанного `--dry-run`.

## Особое внимание при ревью

1. Недоступная либо несуществующая ссылка: одинаковый отказ без раскрытия данных.
2. Приведение типов 1С не должно молча округлять число или обрезать строку.
3. Процент, подчёркивание и квадратные скобки в поиске — обычные символы.
4. Обязательность строк и условные правила БСП не подменяются статической схемой.
5. Неудачная проверка или запись не оставляет частично записанного документа.

## Файлы и ответственность

- `src/extensions/СчетаМагазина/Configuration.xml`, `ConfigDumpInfo.xml` и XML объектов:
  состав расширения, серверные общие модули, маршруты HTTP-сервиса.
- `CommonModules/СчетаМагазинаМетаданные/Ext/Module.bsl` внутри расширения:
  метаданные документа, описание полей и типов, разрешённые справочники.
- `CommonModules/СчетаМагазинаДанные/Ext/Module.bsl` внутри расширения:
  строгие преобразования JSON, заполнение объекта, поиск, чтение сохранённого счёта.
- `HTTPServices/СчетаМагазина/Ext/Module.bsl` внутри расширения:
  транспорт, HTTP-ошибки, сообщения проверки, транзакция создания, журнал регистрации.
- `src/tests/shop-invoices.test.mjs`: реальные HTTP-проверки без зависимостей;
  адрес и авторизацию читать из игнорируемого `.env` рядом с тестом.
- `src/tests/shop-invoices.http`: последовательность сценариев для REST Client.

### Task 1: Расширение и проверяемый HTTP-контракт

**Интерфейсы:**

- Модуль метаданных: `Документ()` → метаданные целевого документа;
  `Схема()` → структура описания из спецификации;
  `РазрешенныеСправочники()` → соответствие имени справочника его метаданным;
  `ОписаниеПоля(Реквизит, ДоступенДляЗаписи)` → структура поля.
- Модуль данных: `Подготовить(Данные, Ошибки)` → структура типизированных шапки и таблиц;
  `Заполнить(Объект, Данные)`; `НайтиВСправочнике(Имя, СтрокаПоиска, Лимит)` → результат поиска;
  `Прочитать(Идентификатор)` → сохранённые данные либо `Неопределено`.
- Обработчики сервиса принимают HTTP-запрос, возвращают HTTP-ответ;
  имена обработчиков и URL согласованы с XML сервиса.

- [x] Написать HTTP-тесты чтения схемы: `200`, корректный UTF-8 JSON, все реквизиты
  и таблицы из XML основной представлены; обязательность совпадает с метаданными;
  у ссылок есть адрес поиска, у перечислений — значения; запрещённые поля явно помечены.
- [x] Написать тесты поиска: подстрока, допустимый лимит, признак неполной выдачи,
  неверный лимит, пустая строка, запрет чужого справочника, экранирование шаблонов.
- [x] Написать тесты создания: успешный POST и независимый GET; сохранены ссылки,
  суммы и отсутствие проведения. Контрольное создание запускается отдельным флагом.
- [x] Написать отказы: неверный JSON и хвост, неправильная структура, неизвестное поле,
  недоступное поле, неверный UUID, несуществующая ссылка, строка вместо числа,
  превышение точности и длины, некорректная дата и часовой пояс, отсутствие обязательного
  реквизита и обязательного поля строки. Проверять `error.details`, а не только статус.
- [x] Запустить HTTP-тесты до реализации. Ожидается отказ на отсутствующем сервисе;
  записать RED в журнал. До отправки POST проверить, что сервис действительно отсутствует.
- [x] Создать XML по каркасу скилла с новыми UUID и серверными непривилегированными модулями.

- [x] Реализовать интерфейсы метаданных, данных и транспорта. Запросы параметризованные;
  динамические имена таблиц только из разрешённого набора. Преобразование значений

- [x] Запустить `scripts/onec-stand check-xml src/extensions/СчетаМагазина --base 1c/config`

- [x] Провести независимое ревью источников и тестов, устранить существенные замечания.
- [x] Выполнить preflight и показать пользователю

**Интерфейсы:** использует публичные методы задачи 1 и локальный `.env` тестов.

  Адрес, авторизация и UUID — переменные `.env`; числа примера — литералы с пометкой.
- [x] Подобрать существующие данные через разрешённый поиск. Проверить, что штатная
  проверка дополнительных свойств не блокирует создание; если блокирует — согласовать
  изменение границ вместо обхода штатной проверки.

## Особенности исполнения

План выполняется в существующей чистой рабочей копии на ветке задачи: перенос в другую
копию не требуется для этой последовательной работы со стендом проекта.
HTTP RED выполняется до кода, GREEN — после согласованной загрузки: отдельного
интерпретатора BSL вне базы здесь нет. До загрузки задача не считается проверенной.
Это ограничение среды записывается в журнал, а не подменяется проверками текста BSL.

Проверка плана автором: разделы спецификации распределены между задачами;
интерфейсы модулей согласованы; особые случаи перечислены в тестах задачи 1,
отсутствие записи после отказа и условие БСП проверяются в задаче 2.
