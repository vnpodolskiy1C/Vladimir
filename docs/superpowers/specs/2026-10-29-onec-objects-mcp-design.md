## Назначение

Менеджер отдела продаж пишет просьбу в чат ИИ-ассистента и работает с базой,
не открывая 1С. Ассистент из нового чата, без знания конфигурации и без вставленных
в чат адреса и учётных данных, находит тип, узнаёт поля, подбирает ссылки и создаёт
объект. Контрольный пример — непроведённый счёт на оплату покупателю: ассистент
называет номер из ответа, счёт открывается в 1С, покупатель и товар заполнены.

Сервер даёт ассистенту инструменты над уже работающим сервисом объектов. Смысл
ответов сервиса задаёт [спецификация сервиса](2026-10-25-object-service-design.md).
Этот документ задаёт, как инструменты MCP отображаются на её маршруты и как
ассистент отличает ответ сервиса от недоступности.

Решения пользователя в текущей сессии перечислены в разделах инструментов, описаний
и границ. Выбор среды выполнения и прочие технические решения, которых не было
в постановке, помечены как решения исполнителя.

Адрес публикации и учётные данные в репозиторий не попадают: их задаёт окружение.

## Цели

- Новый чат ассистента в проекте видит пять инструментов сервера `onec-objects`.
- По описанию инструмента модель понимает, что он делает, когда его вызывать
  и что вернётся.
- Ответ сервиса, включая `hasMore` и JSON отказа, доходит до ассистента без
  переработки.
- Инструмент создания помечен изменяющим, остальные — только читающими, чтобы
  клиент ассистента спросил подтверждение перед изменением базы.
- Недоступность сервиса отличается от отказа 1С.
- Адрес сервиса, пользователь и пароль не записаны ни в коде сервера,
  ни в его подключении.

## Вне целей

- Изменение, удаление и проведение объектов.
- Доработка сервиса объектов и расширения.
- Удалённый доступ к серверу по сети: сервер локальный, его запускает клиент
  ассистента.
- Подбор одной ссылки из нескольких совпадений, расчёт сумм, заполнение полей
  счёта и любые другие правила 1С в коде сервера.
- Повторный HTTP-запрос силами сервера и поиск объекта силами сервера после
  создания.
- Приёмка контрольного примера из нового чата. Её проводит пользователь.
  Исполнитель доводит сервер до автоматических проверок этого документа и
  подключает его в проекте.

## Антицели

Провал, даже если процесс сервера запускается:

- ассистенту снова нужны адрес публикации или учётные данные в чате;
- описание инструмента перечисляет прикладные поля счёта, партнёра или товара;
- сервер обрезает, переименовывает или заново сериализует JSON сервиса;
- повтор создания прячется, склеивается с предыдущим или выполняется сервером
  сам, когда ответ создания неясен;
- инструмент создания помечен только читающим.

## Ограничения

- Сервис объектов не меняется. Корень сервиса — `objects`, шаблоны —
  `/types`, `/type`, `/search`, `/object`.
- Сервер ходит в базу только HTTP-запросами к этому сервису.
- Каталог сервера — `src/mcp/onec-objects/`. Запись подключения —
  конфиг агента, правится вручную. Запуск — собранный файл по пути от
  корня проекта.
- Адрес сервиса, пользователя и пароль 1С процесс при старте берёт из
  переменных окружения `OBJECT_SERVICE_URL`, `OBJECT_SERVICE_USER`,
  `OBJECT_SERVICE_PASSWORD`.
- Зависимости и каталог сборки в git не входят. Перед подключением их ставят
  и собирают командами из `package.json` сервера.
- Клиент ассистента — Cursor. Подтверждение перед вызовом — поведение клиента
  по пометке инструмента. Сервер диалог подтверждения не рисует и режим
  запусков клиента не настраивает.

## Подходы

1. **Node, TypeScript, официальный SDK MCP, транспорт stdio, сборка в `dist`.**
   Выбран исполнителем. В проекте сервер описан через `package.json`, проверки
   уже идут на Node, а SDK отдаёт список инструментов, пометки и вызов по
   stdio. Сборка соответствует правилу «подключение запускает собранный сервер».
2. **Один модуль JavaScript на том же SDK без проверки типов при сборке.**
   Меньше шагов, но правило проекта ждёт сборку, а пометки инструментов как раз
   то, что легко разъехать без типов. Не выбран.
3. **Свой разбор JSON-RPC или сервер на Python.** Python не совпадает с правилом
   `package.json` для сервера проекта. Свой протокол повторял бы ту часть, которую
   уже делает SDK, при том что сама работа сервера — один HTTP-запрос на вызов.
   Не выбраны.

Пользователь от дальнейших вопросов отказался и поручил зафиксировать
спецификацию. Поэтому выбор среды — решение исполнителя, а не отдельно
согласованный вариант.

## Границы сервера

Сервер при старте один раз читает переменные окружения процесса:
`OBJECT_SERVICE_URL` — адрес сервиса объектов до `/hs/objects` включительно,
`OBJECT_SERVICE_USER` — пользователь 1С, `OBJECT_SERVICE_PASSWORD` — пароль,
необязательный, без него пароль пустой. Завершающие `/` адреса отбрасываются.
Если адрес или пользователь не заданы, сервер пишет в stderr, каких переменных
не хватает, и завершается с ненулевым кодом, не открывая сессию MCP. Значения
переменных в сообщениях не печатаются. stdout сервера занят протоколом,
рабочие сообщения пишутся в stderr.

Каждый вызов инструмента выполняет один HTTP-запрос и не повторяет его.
Запросы к адресу публикации идут напрямую и не используют `HTTP_PROXY`,
`HTTPS_PROXY` и `ALL_PROXY`. Перенаправления не следуют. Таймаут запроса —
60 секунд. Заголовок авторизации — Basic пользователя и пароля из окружения,
байты кодируются UTF-8. Тело запроса, заголовок авторизации, адрес,
пользователь и пароль в журнал не пишутся.

Ответ с телом из одного значения JSON передаётся ассистенту текстом тела
как есть, без разбора и повторной сериализации. Успех HTTP (статусы 200–299)
— успешный результат инструмента. Любой другой статус с таким телом —
неуспешный результат инструмента, текст которого есть это тело. Так отказ
1С, включая `validation_failed` и `internal_error`, остаётся JSON сервиса.

Недоступность — отдельный неуспешный результат. Его текст начинается с
`Сервис объектов недоступен.` и дальше называет причину. В нём нет JSON
сервиса, адреса, базы, пользователя и тела чужого ответа. Сюда относятся
отказ соединения, таймаут, обрыв, перенаправление, пустое тело, тело не из
одного JSON и тело, которое не декодируется как UTF-8. Сервер в этом случае
новый запрос не делает: если создание уже могло записаться, номер ассистенту
неизвестен, и дальше он действует по описанию `create_object`.

Неверный вызов инструмента обнаруживается до HTTP. Текст начинается с
`Неверный вызов инструмента.` Это не отказ сервиса и не недоступность.

## Инструменты

Имя сервера в протоколе и в записи подключения — `onec-objects`.
Имена инструментов латинские. Заголовки и описания — русские, дословно
как ниже. Описания не содержат прикладных имён реквизитов конфигурации.

Общая инструкция сервера, если клиент показывает её модели:

```text
Сервис объектов 1С. Тип, поля и ссылки узнавай инструментами, конфигурацию заранее не предполагай. Ответ сервиса читай как есть: hasMore значит, что найдено не всё, а отказ — это JSON сервиса. Создание меняет базу.
```

Пометки протокола MCP — подсказки клиенту, не проверка внутри сервера.
У читающих инструментов `readOnlyHint` истина, `destructiveHint` ложь,
`idempotentHint` истина, `openWorldHint` истина. У `create_object`
`readOnlyHint` ложь, `destructiveHint` ложь, `idempotentHint` ложь,
`openWorldHint` истина: вызов добавляет объект, повтор записывает второй,
данные лежат во внешней базе.

Лишние аргументы в HTTP не попадают. Обязательный аргумент отсутствует,
имеет иной JSON-тип или `header` / `tables` является массивом либо `null` —
это неверный вызов, запрос не отправляется. `limit`, если он есть, —
целое число JSON; дробное число и строка — неверный вызов. Значение целого,
в том числе вне диапазона сервиса, уходит в запрос без подстановки и без
ограничения на стороне сервера. Отсутствие `limit` означает, что параметра
`limit` в запросе нет.

Параметры URL кодируются `encodeURIComponent`. В таблице нет `limit`, если
аргумент не передан.

| Инструмент | Заголовок | Метод и путь | Параметры |
| --- | --- | --- | --- |
| `find_types` | Найти типы | `GET /hs/objects/types` | `q`, затем `limit` |
| `describe_type` | Описать тип | `GET /hs/objects/type` | `name` |
| `find_objects` | Найти объекты | `GET /hs/objects/search` | `type`, `q`, затем `limit` |
| `read_object` | Прочитать объект | `GET /hs/objects/object` | `type`, `id` |
| `create_object` | Создать объект | `POST /hs/objects/object` | тело JSON |

Тело создания — объект ровно с ключами `type`, `header`, `tables` и
значениями одноимённых аргументов. Кодировка UTF-8.
`Content-Type: application/json; charset=utf-8`.

### Аргументы

`q` у `find_types`: «Слово для поиска по техническому имени или синониму типа.»

`limit` у обоих поисков: «Необязательный предел выдачи. Без аргумента сервис применяет свой предел. Переданное целое уходит в сервис как есть.»

`name` у `describe_type`: «Полное техническое имя типа в форме Вид.Имя.»

`type` у поиска, чтения и создания: «Полное техническое имя типа в форме Вид.Имя.»

`q` у `find_objects`: «Строка поиска. У справочника это часть наименования, у документа — номер.»

`id` у `read_object`: «Идентификатор объекта из поиска или создания.»

`header` у `create_object`: «Шапка объекта. Состав полей берётся из описания типа.»

`tables` у `create_object`: «Табличные части объекта. Состав берётся из описания типа.»

Обязательны все аргументы, кроме `limit`.

### Описания

`find_types`:

```text
Ищет типы справочников и документов по вхождению слова в техническое имя или синоним. Вызывать, когда нужно узнать, какие типы есть в базе. q — искомое слово. limit необязателен: без него сервис сам ограничивает выдачу. Ответ сервиса приходит как есть. items — найденные типы; hasMore true значит, что найдено не всё. Отказ сервиса приходит его JSON.
```

`describe_type`:

```text
Возвращает описание одного типа: поля, типы значений, обязательность, куда искать значение ссылки и шаблон тела создания. Вызывать перед заполнением объекта и когда нужно понять поле. name — полное техническое имя из поиска типов. Ответ сервиса приходит как есть. Состав полей брать из этого ответа.
```

`find_objects`:

```text
Ищет объекты одного типа: у справочника по наименованию, у документа по номеру. Вызывать, чтобы подобрать ссылку по части наименования или найти документ по номеру. type — полное имя типа, q — строка поиска. limit необязателен: без него сервис сам ограничивает выдачу. Ответ сервиса приходит как есть. items — найденные объекты, идентификатор объекта — id; hasMore true значит, что найдено не всё. Отказ сервиса приходит его JSON.
```

`read_object`:

```text
Читает один объект целиком. Вызывать, когда тип и идентификатор уже известны. type — полное имя типа, id — идентификатор из поиска или создания. Ответ сервиса приходит как есть. Отказ сервиса приходит его JSON.
```

`create_object`:

```text
Создаёт один объект и меняет базу. Вызывать, когда тип, поля и ссылки уже взяты из описания типа и поиска. type, header и tables — тело, которого ждёт сервис; состав полей брать из описания типа. Успешный ответ сервиса приходит как есть: у документа в нём есть номер. Отказ 1С приходит JSON сервиса без переработки; по этому тексту исправить вызов или спросить менеджера. Повторный вызов записывает второй объект. Если ответ неясен и в нём виден номер, сначала найти документ этого типа по номеру через find_objects и не создавать снова. Если номера в неясном ответе нет, спросить менеджера и не вызывать создание снова, пока он не подтвердит.
```

Неясный ответ, поиск по номеру и вопрос менеджеру — указание модели в этом
тексте. Код сервера после создания поиск не выполняет и создание не повторяет.

## Подключение

Запись подключения в конфиге агента называет сервер `onec-objects`. Команда —
`node`, аргумент — `src/mcp/onec-objects/dist/index.js` от корня проекта.
Переменные окружения задаются вне репозитория; если конфиг агента лежит
в git, адреса и пароля в нём нет.

В каталоге сервера есть `package.json` и краткий `README` с командами
установки зависимостей, сборки и проверок. В README нет адреса, базы и
пользователя. Сборка пишет `dist/index.js`. Lock-файл зависимостей
фиксирует версии и входит в git; каталоги зависимостей и `dist` — нет,
они уже закрыты корневым `.gitignore`.

## Проверка

Автоматические проверки живут рядом с сервером и запускаются его командой
проверки. Живая публикация и 1С им не нужны: окружение и HTTP подменяются. Проверки подтверждают:

- пять инструментов с дословными именами, заголовками, описаниями,
  описаниями аргументов и пометками из этого документа, общую инструкцию
  сервера;
- пути, методы и порядок параметров, кодирование кириллицы в параметре,
  отсутствие `limit`, когда аргумент не передан, и передачу переданного
  целого без изменения;
- тело создания ровно из трёх ключей и заголовок `Content-Type`;
- успешное тело и JSON отказа возвращаются той же строкой, что пришла,
  а отказ помечен неуспехом инструмента;
- недоступность и неверный вызов начинаются со своих фиксированных фраз,
  не содержат JSON сервиса и не вызывают HTTP, когда вызов ещё неверен;
- запрос создания не повторяется и после него сервер сам не ищет объект;
- запросы к публикации не идут через прокси окружения и не следуют
  перенаправлениям;
- авторизация — Basic пользователя и пароля из окружения;
- без адреса или пользователя в окружении сервер не открывает сессию
  и не принимает вызовы инструментов.

Успешный пустой поиск с `hasMore false` допустим как ответ сервиса и
передаётся как есть. Он не заменяет проверку, что непустое `items` и
`hasMore true` тоже доходят без изменений.

Приёмка пользователем из нового чата, после установки зависимостей и
сборки: чат видит инструменты; по просьбе словами ассистент создаёт
счёт на оплату покупателю только этими инструментами; перед созданием
клиент спрашивает подтверждение; счёт открывается в 1С по номеру из
ответа, покупатель и товар заполнены, счёт не проведён. Этот проход
исполнитель не подменяет чтением HTTP и не объявляет выполненным.

## Что остаётся исполнителю

Раскладка файлов внутри `src/mcp/onec-objects/`, версия SDK на момент
сборки, настройки TypeScript и способ подмены HTTP в проверках. Выход
сборки, команды и наблюдаемое поведение — как в этом документе.
Версия SDK фиксируется lock-файлом. Пакет не публикуется в реестр.
