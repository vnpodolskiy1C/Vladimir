# Создание счетов покупателям из интернет-магазина

Статус: утверждена пользователем в текущей сессии. Источник требований — ТЗ в текущей
сессии. Выбран первый вариант: магазин передаёт обязательные реквизиты и суммы.

## Назначение и границы

Разработчик магазина без доступа к 1С получает описание счёта, подбирает существующие
ссылки и составляет запрос. Магазин создаёт непроведённый счёт сразу после заказа.
Менеджер проверяет результат в 1С. Ошибка заполнения не оставляет записанного счёта.

Основная конфигурация не меняется. Расширение работает с документом из
[выгрузки метаданных](../../../1c/config/Documents/_ДемоСчетНаОплатуПокупателю.xml).
Состав его реквизитов не фиксируется вручную ни в сервисе, ни в документации.
Адрес публикации и пользователь берутся средствами стенда из конфигурации проекта;
правила — [AGENTS.md](../../../AGENTS.md).

Проведение, изменение, удаление, создание элементов справочников и работа с другими
документами не входят в задачу. Сервис не рассчитывает цены, скидки, НДС и суммы и не
подбирает реквизиты по умолчанию. Каждый успешный запрос создания создаёт новый счёт:
защиты от повторов по идентификатору заказа нет. После потери ответа нельзя считать
повтор безопасным.

## Рассмотренные подходы

1. Прямое заполнение по описанию метаданных. Магазин передаёт обязательные значения,
   сервис преобразует типы и запускает штатную проверку. Выбран пользователем:
   понятное поведение без скрытого выбора значений.
2. Сервис с автозаполнением и пересчётами. Запрос короче, но нужны отдельные правила
   выбора служебных реквизитов и расчёта сумм. Не выбран.

## Размещение и HTTP-контракт

Расширение и HTTP-сервис называются `СчетаМагазина`, RootURL — `shop-invoices`.
Выгрузка расширения размещается в `src/extensions/СчетаМагазина/`.

Пути ниже указаны относительно корня сервиса:

| Метод и путь | Назначение | Успешный статус |
| --- | --- | --- |
| `GET /schema` | Описание счёта и правил передачи значений | `200` |
| `GET /catalogs/{name}?q=…&limit=…` | Поиск существующих элементов справочника | `200` |
| `POST /invoices` | Создание счёта | `201` |
| `GET /invoices/{id}` | Чтение счёта для проверки результата | `200` |

Других операций сервис не предоставляет. Доступ — обычная аутентификация HTTP-сервисов
базы учётной записью 1С, с её правами. Привилегированный режим не включается.
В частности, возможность прочитать или создать документ определяется правами базы.

Тела запросов и ответов — JSON в UTF-8. У ответов
`Content-Type: application/json; charset=utf-8`, без BOM. Для создания клиент
передаёт `Content-Type: application/json`, допустим параметр `charset=utf-8`.

Пример формы запроса, а не перечень полей счёта:

```json
{
  "header": {"Дата": "2026-10-25T10:30:00", "Комментарий": "Заказ магазина"},
  "tables": {"Товары": []}
}
```

Объекты `header` и `tables` обязательны. Имена реквизитов и табличных частей —
технические имена из `/schema`. Необязательные значения можно не передавать.
Отсутствующие значения остаются штатными пустыми значениями нового объекта.
Неизвестные ключи и передача полей, запрещённых для записи, отклоняются.

## Описание по метаданным

Схема формируется при запросе по метаданным действующей конфигурации с расширениями.
Новый реквизит или табличная часть появляется в ней автоматически. Произвольные
метаданные по пользовательскому имени сервис не раскрывает.

Ответ содержит `document`, `fields`, `tables` и `rules`. Для реквизита возвращаются:

- `name`, `title`, `writable`, `required`, `types`;
- ограничения строки и числа, части даты — для соответствующего типа;
- `catalog` и `searchUrl` — для ссылки на разрешённый справочник;
- `values` с техническими именами и представлениями — для перечисления;
- `reason` — если поле недоступно для записи.

Для табличной части возвращаются `name`, `title`, `writable`, `required`, `fields`
и при необходимости `reason`. `required` у поля берётся из проверки заполнения
метаданных; у табличной части — из её настройки. Обязательность поля строки сама
по себе не означает обязательность хотя бы одной строки.

`rules` поясняет, что окончательное решение принимает штатная проверка заполнения:
она может зависеть от данных и настроек базы. Схема не обещает вывести условные
правила из произвольного кода обработчиков.

Стандартные реквизиты тоже описываются. Дата доступна для записи и обязательна.
Номер назначает 1С; ссылка, номер, пометка удаления и признак проведения недоступны
для записи. Запрет стандартных технических полей — правило сервиса, а не копия
перечня прикладных реквизитов.

### Значения JSON

| Тип | Передача |
| --- | --- |
| Строка | Строка JSON с проверкой ограничения длины |
| Число | Число JSON с проверкой разрядности, точности и допустимого знака |
| Булево | `true` или `false` |
| Дата | Строка ISO 8601; дата-время без зоны — местное время базы, поле с частью «Дата» — `YYYY-MM-DD` |
| Одна ссылка на справочник | Строка UUID; тип и адрес поиска указаны в схеме |
| Одно перечисление | Техническое имя значения строкой |
| Составной тип | Объект `{"type": "…", "value": …}`; допустимые имена типов указаны в схеме |

В этой версии даты со смещением или `Z` отклоняются: 1С хранит дату документа без
часового пояса, поэтому сервис не делает неявных преобразований времени.
`null` означает штатное пустое значение соответствующего поля; для составного типа
можно передать типизированное пустое значение. Обязательность проверяет 1С.
Сервис не допускает молчаливого обрезания строк, округления чисел и преобразования
строк в числа или булевы значения.

Ссылка должна указывать на существующий, доступный пользователю элемент допустимого
справочника. Группа и помеченный на удаление элемент не принимаются. Ошибка не
раскрывает, существует ли недоступный пользователю элемент.

### Основание и дополнительные свойства БСП

Ссылки на документы и другие объекты вне справочников, а также табличная часть
дополнительных свойств БСП описываются, но недоступны для записи в этой версии.
Для них `writable=false` с объяснением ограничения; отсутствие поискового метода
не маскируется ссылкой на поиск справочника.

Это ограничение допустимо, только если на стенде можно создать корректный счёт без
дополнительных свойств. Обработчик
[проверки БСП](../../../1c/config/CommonModules/УправлениеСвойствамиСлужебный/Ext/Module.bsl)
проверяет обязательные свойства, настроенные в данных базы. При проверке стенда
необходимо подтвердить отсутствие препятствия контрольным созданием счёта.
Если оно есть, реализацию этой части остановить и согласовать поддержку свойств;
не отключать проверку, не менять настройки базы и не подставлять выдуманные значения.

Для нового типа, который сервис не умеет преобразовывать, схема сохраняет описание
метаданных и явно помечает поле недоступным для записи. Если такое поле обязательно,
это препятствие созданию, а не повод ослаблять проверку заполнения.

## Поиск

Разрешённые справочники определяются из типов реквизитов счёта и его табличных частей.
Имя из URL сверяется с этим набором до построения запроса. Поиск других объектов
запрещён; пользовательский ввод не исполняется и не подставляется в текст запроса.

`q` — непустая после удаления внешних пробелов часть наименования. Символы шаблона
поиска трактуются как обычные символы. `limit` — целое число от 1 до 100,
по умолчанию 20. Неверные параметры отклоняются. Сортировка — по наименованию,
затем ссылке; запрос получает не более `limit + 1` элементов.

Ответ: `items`, `hasMore`. Элемент содержит `id` и `name`. Возвращаются только
доступные пользователю элементы без пометки удаления, не группы. `hasMore=true`
означает, что клиенту следует уточнить строку поиска или увеличить допустимый лимит;
постраничной выдачи в этой версии нет.

## Создание и чтение

Порядок создания:

1. Полностью разобрать JSON, включая проверку отсутствия хвоста после значения.
2. Проверить структуру, поля и значения по схеме. Подготовить значения с точными
   типами 1С без записи прикладных объектов.
3. Создать объект счёта, перенести шапку и строки. Не вызывать автозаполнение формы
   или обработку заполнения нового документа.
4. В транзакции очистить очередь сообщений, вызвать штатную `ПроверитьЗаполнение()`
   и собрать её сообщения. При отказе откатить транзакцию и вернуть ошибку.
5. Записать в режиме записи без проведения. Проверить, что документ не проведён.
6. Подготовить ответ и завершить транзакцию; при исключении откатить её.

Успешный ответ содержит `id`, `number`, `date`, `posted=false`. Для даты ответа
используется ISO 8601 без часового пояса. Запись с флагом обмена, обходящая штатные
обработчики, запрещена.

Чтение по UUID возвращает `id`, `number`, `date`, `posted`, `header` и `tables`.
Шапка и таблицы содержат поля, доступные для записи через данный контракт, в том же
формате значений. Номер, дата, признаки и ссылки читаются из сохранённого объекта,
а не из предыдущего запроса. Не найденный или недоступный счёт даёт `404`.
Чтение после POST позволяет отдельно проверить сохранённые данные.

## Ошибки и журналирование

Форма ошибки:

```json
{
  "error": {
    "code": "validation_failed",
    "message": "Счёт не прошёл проверку заполнения",
    "details": [{"path": "header.Организация", "message": "Текст проверки 1С"}]
  }
}
```

`path` — путь в запросе; если штатное сообщение не даёт достоверно определить поле,
путь равен `null`, текст сохраняется без угадывания. Для строки таблицы путь включает
индекс, начиная с нуля. Возвращаются все полученные сообщения штатной проверки.

| Статус | Причина |
| --- | --- |
| `400` | Неверный JSON, структура, параметры, неизвестное поле, неверный тип или ссылка |
| `403` | Запрошен справочник вне разрешённого набора либо недостаточно прав на операцию |
| `404` | Счёт не найден или недоступен |
| `415` | Неподдерживаемый тип тела запроса |
| `422` | Штатная проверка заполнения отказала; счёт не записан |
| `500` | Неожиданное исключение 1С; при создании транзакция отменена |

Неподдерживаемые HTTP-методы отклоняет маршрутизация HTTP-сервиса платформы.
Аутентификационные отказы также остаются в ведении платформы и публикации.
Собственные ответы обработчиков соответствуют JSON-контракту.

Для сбоя клиент получает краткий текст без стека; подробное представление ошибки
записывается в журнал регистрации с именем события сервиса. Тело запроса и
аутентификационные данные целиком не журналируются.

## Проверка и приёмка

По уточнению пользователя клиентскую часть приёмки — открытие счёта в Предприятии
и сравнение списка документов до и после отказов — выполняет сам пользователь
вручную. Агент не использует Vanessa и не выдаёт HTTP-проверки за проверку формы.

Файл REST Client в `src/tests/` проводит разработчика через описание, поиск ссылок,
успешное создание, чтение результата и отказ по обязательному полю. Адрес и
авторизация берутся из локального игнорируемого `.env` по правилам проекта.
Запрос успешного создания — намеренно запускаемый шаг, а не часть автоматической
подготовки окружения.

На стенде проверяются:

- Применимость расширения, модули и работа каждого метода внешним HTTP-клиентом.
- Соответствие схемы действующим метаданным без ручного списка прикладных полей;
  ограничения типов, справочные ссылки и перечисления описаны автоматически.
- Поиск по подстроке, ограничение выдачи, `hasMore`, запрет постороннего справочника.
- Реально сохранённый счёт: чтение по UUID и открытие в клиенте 1С по номеру из ответа;
  покупатель и товар заполнены, проведение отсутствует, переданные суммы сохранены.
- Запрос без обязательного реквизита и запрос без обязательного поля строки:
  сообщения штатной проверки указывают проблему, новых документов в базе нет.
  Отсутствие записи подтверждается списком документов в клиенте до и после отказа.
- Неверный JSON, тип, UUID, неизвестное поле и недопустимый справочник получают
  клиентские ошибки; отказ после проверки не даёт частичной записи.
- Проверка настроенных дополнительных свойств не мешает контрольному созданию.

Доказательства проверки сохраняются в игнорируемых логах проекта; в отчёте отдельно
указывается, что проверено автоматически, что показано в клиенте и что не проверено.
Не создаются тестовые покупатели, товары или дополнительные настройки без отдельного
согласования: для контрольного примера используются существующие данные.

Все загрузки и проверки идут через CLI стенда. Каждая изменяющая команда стенда
требует отдельного согласования показанного `--dry-run` по правилам проекта.

## Что остаётся исполнителю

Разбиение обработчиков и вспомогательных процедур, XML-каркас расширения,
внутренние структуры для обхода метаданных, инструменты автоматической HTTP-проверки
и подбор существующих данных для контрольного примера. Эти решения не должны менять
описанный публичный контракт, обходить штатную проверку или добавлять новые операции.

После утверждения этой спецификации составляется отдельный план реализации.
