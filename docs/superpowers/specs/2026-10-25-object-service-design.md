## Назначение

Разработчик внешней системы и его ИИ-ассистент находят подходящий тип, получают
описание полей и значений, подбирают ссылки и создают объект без документации по
конфигурации. Партнёр, поступление и счёт используют общий механизм, без списка
прикладных полей в коде сервиса. Сервис читает и проведённые документы, но создаёт
только непроведённые.

Спецификация утверждена пользователем. В разделе границ зафиксированы решения
пользователя; конкретная форма JSON и остальные технические решения предложены
исполнителем и утверждены вместе с документом.

Ограничения платформы, каталоги, режим работы со стендом и правила обращения с
секретами — в [AGENTS.md](../../../AGENTS.md). Совместимость сверяется с
[основной конфигурацией](../../../1c/config/Configuration.xml), состав прикладных
метаданных читается из её выгрузки и действующей конфигурации базы.

## Границы универсальности

Самостоятельные типы объектов — справочники и документы действующей конфигурации
с расширениями. Перечисления описываются как типы значений полей, а не как объекты
для маршрутов поиска и создания. Другие виды метаданных самостоятельными типами
не поддерживаются. Регистры, константы, отчёты и обработки вне контракта.

Поддерживаются элементы иерархических и подчинённых справочников. Клиент явно
передаёт родителя и владельца там, где они нужны. Группы доступны для поиска,
чтения и выбора родителя, но не создаются. В обычных ссылочных реквизитах группы
не принимаются: разрешение группы относится к полю родителя. Допустимый тип
владельца определяется метаданными; сервис не выбирает владельца самостоятельно.

Для записи поддерживаются ссылки на справочники, документы и значения
перечислений. Прочие ссылочные значения описываются и возвращаются при чтении,
но записывать их нельзя. Для них не обещаются маршруты поиска и чтения целевого
объекта. Ссылка не означает включения её целевого вида в самостоятельные типы.

Составные поля поддерживаются по отдельным вариантам: наличие неподдерживаемого
варианта не запрещает записать поддерживаемый. Доступность каждого варианта
показывается в схеме. Неподдерживаемый выбранный вариант отклоняется до записи.

Отдельный платформенный UUID и дата с частью «Время» поддерживаются для чтения
и записи как простые значения по правилам раздела значений JSON. Двоичные данные
и хранилища значений не поддерживаются.

Общие прикладные реквизиты включаются по действующему составу и автоиспользованию
метаданных. Общие реквизиты с разделением данных — служебные разделители платформы;
они исключены из схемы, чтения и создания, управление ими остаётся у платформы.
Граница согласована пользователем при исправлении пропуска общих реквизитов
на итоговом ревью (2026-10-25).

Чтение полное: все применимые стандартные и прикладные реквизиты, табличные части
и их строки, включая поля и таблицы, запрещённые для записи. Нельзя пропустить поле,
подменить неподдерживаемое значение строковым представлением или вернуть частичный
успех. Если фактическое значение нельзя сериализовать, весь запрос чтения получает
отказ с точным путём поля и названием типа. Наличие неподдерживаемого варианта
в метаданных само по себе не мешает чтению, если сохранённое значение поддерживается.

Табличная часть дополнительных реквизитов БСП описывается и читается, но целиком
закрыта для записи. Специального механизма выбора свойств и их заполнения нет.
Обязательные дополнительные реквизиты могут препятствовать созданию объекта;
штатная проверка возвращает отказ. Сервис не отключает её и не меняет настройки.
Основание такого поведения —
[проверка БСП](../../../1c/config/CommonModules/УправлениеСвойствамиСлужебный/Ext/Module.bsl).

Изменение, удаление, проведение, создание предопределённых элементов, автоподбор
прикладных значений, расчёт цен и сумм, заполнение форм, файловый обмен и защита
от повторного создания не входят в контракт. Потеря ответа POST не делает его
повтор безопасным. Обычные обработчики объекта при проверке и записи выполняются.

## Подход

Общий механизм перечисляет допустимые метаданные, строит описание полей, проверяет
и преобразует JSON, затем обращается к менеджеру выбранного типа. Имя из запроса
сначала точно сверяется с построенным набором типов. Текст запроса к данным может
содержать только имена, полученные из уже проверенных метаданных. Значения клиента
передаются параметрами; выполнение клиентского текста запрещено.

Адаптеры конкретных документов и справочников требуют доработки для каждого нового
типа и не выполняют цель универсальности. Перенос автозаполнения из форм тоже требует
отдельных правил для типов и меняет поведение существующего сервиса. Поэтому для
выбранных границ используется единый механизм с явной передачей значений клиентом.

Существующее расширение не переименовывается. HTTP-сервис имеет единственный
корень `objects`; прежний корень и шаблоны URL сервиса счетов удаляются, совместимые
обёртки не предусматриваются. Имя расширения и идентичность сервиса сохраняются
в [описании расширения](../../../src/extensions/СчетаМагазина/Configuration.xml)
и [описании сервиса](../../../src/extensions/СчетаМагазина/HTTPServices/СчетаМагазина.xml).
Соответствие `RootURL` и шаблонов этому контракту проверяется автоматически.
Счёт создаётся общим маршрутом с указанием типа. Старая спецификация счёта
не задаёт контракт новых маршрутов.

## Общие правила обмена

Запросы и ответы — JSON в UTF-8. Ответ содержит
`Content-Type: application/json; charset=utf-8`, без BOM. POST принимает
`application/json` с необязательным `charset=utf-8`; другие типы и кодировки
отклоняются. JSON должен содержать одно значение без хвоста. Обработка повторяющихся
ключей JSON вне объёма: специальный детектор и отдельные гарантии не предусматриваются.

Имя самостоятельного типа — точное полное техническое имя из метаданных в форме
`Вид.Имя`. Примеры из ТЗ: `Справочник._ДемоПартнеры` и
`Документ._ДемоСчетНаОплатуПокупателю`. Имена в JSON — технические имена, синонимы
служат для подсказок. Все параметры URL кодируются по правилам URL, включая имена
на кириллице. Неизвестные параметры запроса отклоняются; повтор одного параметра
отклоняется, если его повтор доступен обработчику платформы. Если платформа уже
свернула повторяющиеся параметры в одно значение, контракт применяется к этому
значению. Неизвестные поля тела и служебные поля, закрытые для записи, отклоняются.

Аутентификацию выполняет публикация базы. Сервис работает с правами пользователя
1С без привилегированного режима и учитывает ограничения доступа к данным.
Поиск типов показывает только типы с правом чтения или добавления; флаги операций
отражают эти права и известные ограничения метаданных, но не гарантируют успех
проверки заполнения, доступа к конкретной записи или полного чтения её значений.

## Маршруты

Все пути относительны корню сервиса. `limit` у поисковых маршрутов необязателен:
целое число от 1 до 100, по умолчанию 20; остальные параметры обязательны.

| Метод | Путь | Успех |
| --- | --- | --- |
| GET | `/types?q=<слово>&limit=<число>` | `200` |
| GET | `/type?name=<Вид.Имя>` | `200` |
| GET | `/search?type=<Вид.Имя>&q=<строка>&limit=<число>` | `200` |
| GET | `/object?type=<Вид.Имя>&id=<uuid>` | `200` |
| POST | `/object` | `201` |

Неподдерживаемые методы, неизвестные пути и аутентификационные отказы обрабатывает
платформа и веб-сервер; для их собственных ответов JSON не обещается. Каждый ответ
вызванного обработчика сервиса соответствует этому контракту.

### Найти тип

Поиск регистронезависимый, по вхождению `q` в техническое имя или синоним типа.
Внешние пробелы удаляются; пустой результат нормализации отклоняется. Символы
шаблонов поиска считаются обычными символами. Порядок — по полному имени типа.

Ответ — `{"items": [...], "hasMore": false}`. Элемент содержит `name` с полным
именем типа, `title` с синонимом, `kind` (`catalog` или `document`),
`descriptionUrl` для получения схемы и `operations` с описанием доступности
`search`, `read`, `create`. Каждая операция имеет `allowed` и `reason`:
при разрешении причина равна `null`, при запрете — понятный текст.
После ограничения выдачи `hasMore=true` означает, что совпадений больше лимита.
Сортировка и ограничение применяются после проверки прав на типы.

### Описать тип

Ответ содержит `name`, `title`, `kind`, `operations`, `fields`, `tables`,
`exchange`, `rules`. Схема формируется из действующих метаданных, включая
определяемые типы. Добавление прикладного поля или таблицы не требует правки
сервиса. В схеме нет вручную перечисленных реквизитов счёта, партнёра или поступления.

Описание поля:

- `name`, `title`, `standard`, `appliesTo`, `required`, `readable`, `writable`, `reason`, `types`;
- `required` — признак проверки заполнения в метаданных; окончательное решение
  принимает штатная проверка с учётом кода и настроек базы;
- `types` — варианты типа с собственными `name`, `kind`, `readable`, `writable`,
  `reason`, квалификаторами и правилами кодирования;
- `readable` или `writable` поля истинно, если есть хотя бы один соответствующий
  вариант и сама политика поля разрешает операцию. Доступность конкретного
  значения определяется также выбранным вариантом и правами. `reason` объясняет
  полный либо частичный запрет, иначе равен `null`.

Описание табличной части содержит `name`, `title`, `appliesTo`, `required`, `readable`,
`writable`, `reason`, `fields`. Все таблицы и поля присутствуют независимо от
возможности записи. Обязательность поля строки сама по себе не требует наличия
строк. Стандартный номер строки описывается, читается и не записывается клиентом.

`appliesTo` — массив допустимых контекстов: `item`, `folder` для справочника,
`document` для документа. Для справочника применимость поля или таблицы берётся
из метаданных использования для элемента и группы. Поле только для группы не
может стать доступным для записи, поскольку создание групп запрещено.

Для типов значений указываются ограничения длины строки, разрядности и точности
числа, допустимого знака и части даты. Ключи квалификаторов: у строки `length`
и `fixedLength`, у числа `digits`, `fractionDigits`, `nonnegative`, у даты `parts`
со значением `date`, `dateTime` либо `time`. Неограниченная длина
строки обозначается нулём. `kind` принимает `string`, `number`, `boolean`, `date`,
`uuid`, `catalog`, `document`, `enum`, `reference` либо `unsupported`; `reference` обозначает
прочие ссылочные виды, `unsupported` — непредставимый вариант.
Ссылочный вариант содержит `targetType`
с полным именем целевого вида и объекта. Если целевой вид поддерживается как
самостоятельный, также возвращаются шаблоны `searchUrl` и `objectUrl` для выбора
и чтения ссылки; иначе они равны `null`. Значения перечислений раскрываются
в `values` как техническое имя `name` и представление `title`.

`exchange` содержит `createTemplate` — объект с именем типа в `type` и пустыми
`header`, `tables`; `compoundTemplate` — объект с ключами `type`, `value`, где
метка выбирается из `types[].name`; `nullRule` и `dateRule` — текстовые пояснения
по разделу значений; `unknownFields` со значением `reject` и `readMode` со значением
`completeOrError`. Значение в `compoundTemplate` равно `null`, а вместо метки
указана строка `types[].name`: это обозначение места подстановки, не допустимый
тип. Шаблоны показывают структуру, а не готовый валидный объект.
`rules` — массив строк с текстовыми пояснениями о штатной
проверке, отсутствии расчётов, создании без проведения, группах и дополнительных
реквизитах БСП. Схема вместе с поиском позволяет составить запрос без знаний
конфигурации; условные правила произвольного кода 1С статически не выводятся.

Стандартные реквизиты описываются по метаданным. Для документа клиент может
записать дату; она обязательна. Для справочника — наименование, а также родителя
и владельца, если они предусмотрены метаданными и доступны элементу. Их типы,
длина и обязательность берутся из метаданных. Номер документа и код справочника
назначает 1С. Остальные стандартные технические реквизиты доступны только для
чтения. Если объект не поддерживает автоматическое назначение обязательного
номера или кода, `operations.create.allowed=false` с объяснением; запись такого
объекта отклоняется как неподдерживаемый случай. Правила назначения прикладных
реквизитов не угадываются по их названиям. Отсутствие кода или номера как свойства
хранения при нулевой длине не запрещает создание: в кратком ответе соответствующее
значение — пустая строка.

### Найти объекты

У справочников поиск идёт по подстроке наименования, у документов — номера.
Нормализация и трактовка символов `q` такие же, как в поиске типов. Числовой номер
рассматривается в строковом представлении без форматирования групп разрядов.
Нет нужного стандартного поля в метаданных — операция поиска недоступна с
объяснением в схеме и понятным отказом при вызове.

Поиск возвращает только доступные пользователю, не помеченные на удаление объекты.
У справочников выдаются и элементы, и группы. У документов — проведённые и
непроведённые. Подчинённый справочник ищется среди всех доступных владельцев;
фильтра владельца в этой версии нет.

Порядок — по полю поиска, затем ссылке. Из базы запрашивается не более `limit + 1`
совпадений. Ответ — `items` и `hasMore`; в `items` не более `limit` элементов.
Постраничного продолжения нет: клиент уточняет строку либо увеличивает лимит.
Поиск ничего не меняет и не вызывает получение полного объекта ради каждой строки.

Элемент результата всегда содержит `type`, `id`, `name` с представлением.
Для справочника дополнительно возвращаются `code` и `isFolder`, для документа —
`number`, `date`, `posted`. Номер и код в кратких ответах — строки. У справочника
без иерархии групп `isFolder=false`. Идентификатор — UUID, а не представление ссылки.

### Прочитать объект

Ответ содержит краткие поля соответствующего вида из поиска, а также `header`
и `tables`. Шапка включает стандартные и прикладные поля по схеме, применимые к
контексту объекта. Поле или таблица, которые по `appliesTo` относятся только к
элементу, не являются полями группы и не выдаются при её чтении; обратное правило
действует для элемента. Это исключение по метаданным явно описано в схеме и не
используется для пропуска неподдерживаемых значений применимых полей. Каждая таблица
представлена массивом строк; пустая таблица — пустым массивом. Порядок строк
сохраняется, индексы путей ошибок начинаются с нуля.

Группы и помеченные на удаление объекты можно прочитать по известному UUID.
Данные возвращаются из сохранённого объекта, включая признаки проведения,
группы и удаления. Удалённая физически, отсутствующая или недоступная запись
даёт одинаковый ответ о ненайденном объекте. Ошибка синтаксиса UUID отделяется
от отсутствия записи. Само создание ссылки по UUID существование не доказывает.

Если хотя бы одно фактическое значение не поддерживается для чтения, весь ответ —
ошибка `unsupported_value` с путём и типом. Это относится и к дополнительным
реквизитам БСП. Другие ссылочные виды возвращаются по общим правилам ссылок;
произвольное содержимое хранилищ значений не извлекается и не экспортируется.
Неподдерживаемый фактический тип отклоняется даже при пустом значении этого типа;
платформенные `Неопределено` и `Null` возвращаются как JSON `null`.

### Создать объект

Форма тела показана на примере, а не задаёт список полей партнёра:

```json
{
  "type": "Справочник._ДемоПартнеры",
  "header": {"Наименование": "Контрольный партнёр"},
  "tables": {}
}
```

Все поля корня обязательны; `header` и `tables` — объекты. Имена и допустимые
значения внутри них клиент получает из схемы. Каждая переданная табличная часть —
массив объектов строк. Необязательные реквизиты и таблицы можно не передавать:
остаются значения нового объекта, установленные платформой и штатным кодом.
Пример выше иллюстрирует форму и не обещает прохождения проверки заполнения.

Порядок обработки:

1. Проверить тип тела, разобрать JSON, структуру, имя типа, права и доступность
   создания. Полностью проверить и преобразовать значения шапки и строк без записи
   прикладных объектов. Неизвестные и запрещённые поля — ошибки клиента.
2. Начать транзакцию до создания объекта. Создать элемент справочника либо
   документ; перенести подготовленные поля и строки. Отдельно обработку заполнения
   или код формы не вызывать. Не включать режим обмена, обходящий обработчики.
3. Очистить очередь сообщений, выполнить `ПроверитьЗаполнение()` и собрать
   сообщения штатной проверки. Отказ — отмена транзакции и `validation_failed`.
4. Записать справочник обычной записью, документ — в режиме записи без проведения.
   Если обработчик записи отказал без неожиданного исключения, отменить транзакцию
   и вернуть `validation_failed` с полученными сообщениями. Исключение 1С, кроме
   нарушения прав, считается внутренним сбоем, а не угадывается по тексту.
5. Проверить сохранённый признак проведения документа и отсутствие созданной
   группы. Подготовить и сериализовать краткий ответ до фиксации транзакции.
   Зафиксировать транзакцию и вернуть ответ. Любое исключение до фиксации отменяет
   транзакцию; успех без полученной ссылки на записанный объект запрещён.

Успешный ответ — краткое описание по тем же правилам, что элемент поиска.
У документа `posted=false`, у справочника `isFolder=false`. Проверка полного
сохранённого содержимого — отдельным GET; POST не требует, чтобы все поля,
которые штатный код мог заполнить, были доступны для последующего полного чтения.
Известное ограничение чтения заранее видно в схеме.

## Значения JSON

Правила одинаковы для шапки и строк. Сервис не обрезает строки, не округляет числа
и не преобразует строки в числа или булевы значения.

| Вариант | JSON и правила |
| --- | --- |
| Строка | Строка JSON; длина и фиксированность проверяются до присваивания |
| Число | Число JSON; проверяются разрядность, дробная часть и допустимый знак |
| Булево | `true` или `false` |
| Дата | Строка `YYYY-MM-DD` для части «Дата» или `YYYY-MM-DDTHH:mm:ss` для даты со временем |
| Время без даты | Строка `HH:mm:ss`, часы в пределах суток, минуты и секунды в пределах обычного времени |
| Отдельный UUID | Строка UUID в канонической форме с дефисами; не проверяется как ссылка на объект |
| Ссылка на справочник или документ | Строка UUID; целевой тип указан в схеме |
| Перечисление | Техническое имя значения строкой, не синоним |
| Другой ссылочный вид | UUID, только для чтения; целевой вид и имя указаны в схеме |
| Составное поле | Объект с полями `type` и `value`; `type` точно равен `types[].name` |

Метки простых типов — `string`, `number`, `boolean`, `date`, `uuid`; время без даты
имеет метку `date` и квалификатор `parts=time`. Метки ссылок на
справочники, документы и перечисления сохраняют форму существующего обмена:
`CatalogRef.<Имя>`, `DocumentRef.<Имя>`, `EnumRef.<Имя>`. У прочих ссылок и
неподдерживаемых вариантов клиент копирует точную метку из схемы, не конструирует
её по синониму. `targetType` содержит полное имя метаданных и не заменяет метку.

Смещение часового пояса и `Z` запрещены; время трактуется как местное время базы.
Невозможные даты и время отклоняются; дробные секунды и отсутствие ведущих нулей
не допускаются. UUID принимается независимо от регистра шестнадцатеричных букв,
выдаётся в нижнем регистре. Двоичные данные, хранилища значений и прочие неописанные простые типы в этой версии
не преобразуются. Их ограничения явно видны в `types`, а фактическое значение
такого типа вызывает отказ чтения.

`null` для простого поля означает штатное пустое значение его типа, а не отказ
от проверки обязательности. Пустые строки, нули и `false` читаются своими значениями;
пустые ссылки, перечисления и даты — как `null`. Для времени без даты полночь
возвращается строкой `00:00:00`, для UUID нулевое значение остаётся строкой UUID.
Для составного поля клиент может передать типизированное пустое значение
`{"type": "…", "value": null}`. Непосредственный `null` сохраняет прежнюю
семантику — штатное пустое значение полного описания типов; после приведения
сервис проверяет, что выбранный платформой вариант разрешён для записи.
У явно выбранного варианта `null` не обходит его запрет записи.
При чтении составного поля конкретный тип сохраняется в оболочке, даже для пустой
ссылки; если фактическое значение — `Неопределено` или `Null`, возвращается `null`.

Входная ссылка должна существовать, быть доступной пользователю и не иметь
пометки удаления. Группы допустимы только в роли родителя. Для владельца и
родителя дополнительно проверяется соответствие типам метаданных; отсутствие
необходимой связи проверяет штатная проверка 1С. Ссылки на документы могут
указывать как на проведённые, так и на непроведённые документы. Внешний UUID
не даёт возможности изменить существующую запись: поле ссылки закрыто для записи.
Вложенное создание объектов из ссылочных полей не поддерживается.

## Ошибки

Единая форма показана на примере:

```json
{
  "error": {
    "code": "validation_failed",
    "message": "Объект не прошёл проверку заполнения",
    "details": [{"path": "header.Наименование", "message": "Текст проверки 1С"}]
  }
}
```

У детали обязательны `path` и `message`; для неподдерживаемого значения также
возвращается `type` с точной меткой фактического типа. Путь ссылается на поле
запроса или результата, например `tables.Товары[0].Количество`.
Для штатного сообщения, которое нельзя достоверно сопоставить полю, `path=null`.
Сообщения сохраняются без угадывания пути по тексту; пустой отказ проверки получает
общую деталь с `path=null`. При доступной проверке нескольких входных полей
возвращаются все найденные ошибки до попытки записи.

| HTTP | Код и смысл |
| --- | --- |
| `400` | `invalid_json`, `invalid_parameter`, `invalid_type`, `invalid_id`, `invalid_data` — некорректный запрос, неизвестный тип, поле, значение или недопустимая входная ссылка |
| `403` | `forbidden` — нет прав на тип либо операцию |
| `404` | `not_found` — запрошенный объект отсутствует или недоступен |
| `415` | `unsupported_media_type` — неприемлемый Content-Type или кодировка |
| `422` | `unsupported_type` — вид объекта вне контракта; `unsupported_operation` — известное ограничение операции; `unsupported_value` — невозможно полное чтение; `validation_failed` — штатный отказ проверки или записи |
| `500` | `internal_error` — неожиданное исключение 1С |

Неверный синтаксис имени или отсутствующий объект метаданных — `invalid_type`.
Существующий объект метаданных неподдерживаемого вида — `unsupported_type`.
Разрешение имён выполняется через сверку с известными коллекциями метаданных,
без обращения с пользовательским вводом к произвольным исполняющим API.
Для GET объекта отсутствие прав чтения и ограничения на конкретную запись
маскируются одинаковым `404`; для остальных операций отказ в правах — `403`.
Ошибка входной ссылки не раскрывает существование недоступной записи.

Клиент при неожиданном сбое получает общий текст без стека, имён внутренних
модулей и подробностей исключения. Подробности записываются в журнал регистрации
событием HTTP-сервиса; тело запроса, значения полей и учётные данные целиком
не журналируются. Неподдерживаемое значение и штатный отказ не выдаются за сбой 1С.

## Проверка и передача результата

Реализация включает исходники того же расширения, новый файл REST Client
и проверки контракта в каталоге тестов из [карты проекта](../../../AGENTS.md).
Прежние проверки и запросы счёта адаптируются либо заменяются, чтобы не предлагать
к использованию снятые маршруты. Новая спецификация не копирует прикладные поля
из XML; тесты получают независимые ожидания из выгрузки метаданных.

REST Client содержит запрос для каждого маршрута, создание партнёра, поступления
и счёта общим POST, а также чтение результатов и примеры отказов. Реальные ссылки
подбираются через сервис; адрес, авторизация, идентификаторы и остальные локальные
значения находятся в игнорируемом файле переменных рядом с запросами. Синтаксис
подстановки — по правилам проекта. Приёмочные POST выполняются только при явно
включённом флаге создания; полученные UUID сразу сохраняются. Обычный повторный
прогон читает сохранённые объекты без нового POST. После потери ответа повтор
не выполняется автоматически; отдельный автомат состояний и отпечатки запросов
не требуются.

Проверки подтверждают:

- маршруты, статусы, JSON без BOM и соответствие этой спецификации, включая лимиты;
- независимое соответствие схемы метаданным стандартных полей, определяемых и
  составных типов, таблиц и перечислений;
- чтение и запись отдельного UUID и времени без даты, сохранение полуночи,
  отказ по неверным UUID и невозможному времени;
- поиск типов по имени и синониму; поиск справочников, групп и документов;
  непустую ограниченную выдачу с достоверным `hasMore`, буквальную обработку
  специальных символов и недоступность неподдерживаемых видов;
- явную передачу владельца и родителя, запрет создания группы, проверку ссылок
  разных разрешённых видов, отказ неподдерживаемого варианта составного поля;
- полное чтение всех описанных полей и строк, в том числе закрытых для записи,
  и целостный отказ на неподдерживаемом фактическом значении;
- сохранение партнёра, поступления и счёта из тел REST Client, независимое чтение
  записанного, отсутствие проведения и отсутствие созданных объектов после отказов;
- отказ по обязательному реквизиту шапки и строки, неверным типам, неизвестным
  полям, недоступным операциям, некорректному JSON и Content-Type.

Успешный пустой результат не считается проверкой положительного сценария.
Для ограничений, которых нет в данных целевой базы, используются изолированные
тестовые примеры; их создание также подчиняется правилам изменяющих действий
стенда. Нельзя менять настройки основной конфигурации ради прохождения проверки.
Если такие примеры недоступны, соответствующий сценарий перечисляется
непроверенным в итоговом отчёте, а не считается пройденным по статическому просмотру
кода. Отдельный файл-матрица проверок не ведётся.

Применимость расширения, проверка модулей, публикации и внешние HTTP-вызовы
проверяются через стенд. Загрузка, повторная загрузка после исправления и другие
изменяющие действия выполняются только после отдельного согласования показанной
команды согласно правилам проекта; утверждение этой спецификации их не заменяет.

После успешной проверки расширение выгружается в новый локальный `.cfe` в пределах
каталогов проекта; двоичный артефакт не добавляется в git. Для контрольных объектов
передаются UUID и данные для поиска в интерфейсе. Открытие созданных объектов
в клиенте 1С проверяется отдельно; HTTP-чтение не считается доказательством открытия
формы. Клиентскую проверку пользователь выполняет вручную, как предусмотрено
материалами сервиса счёта. Без её выполнения соответствующий пункт
не объявляется завершённым.
